Phundamental.jl

Phundamental.jl is a representation-aware framework for constructing, transforming, solving, and analyzing quantum many-body models in Julia. Symbolic models and explicit transformations feed generic or specialized numerical methods; typed requests describe physical observables, and plan_forward selects routes permitted by the execution policy. The package also represents physical model-space admissibility independently of solver capabilities, generates finite crystallographic invariant Hamiltonian families, selects symmetry-complete structural submodels, and connects them to the forward-physics pipeline.

The central design rule is that the physical model, mathematical representation, numerical approximation, solver backend, observable definition, probe response, and instrumental resolution remain distinct objects. This separation makes transformations auditable, allows optimized backends to replace reference implementations without changing the represented physics, and keeps numerical approximations explicit in results and provenance.

\[\text{material/geometry}\rightarrow\text{Hamiltonian model}\rightarrow\text{representation}\rightarrow\text{optional transformation}\rightarrow\text{solver}\rightarrow\text{observable}\rightarrow\text{probe response}\rightarrow\text{instrument response}\]

The primary model object is ManyBodyModel, whose representation stores the ambient state space, exact physical sector, operator algebra, basis, constraints, gauge information, ordering, reference state, and any numerical truncation. A package-wide invariant is therefore

\[\boxed{\text{ambient state space}\neq\text{physical subspace}\neq\text{numerical truncation}}\]

Physical constraints define the theory being represented. Numerical truncations define how that theory is realized computationally and are never silently reinterpreted as physical constraints.

Documentation map

The manual is organized first by architecture, then by the ten public submodules, and finally by cross-module workflows and validation. Each module page explains the mathematical role of the layer before presenting its API.

  • Getting Started covers loading the package or a source checkout, basic model construction, solver selection, and the high-level forward API.
  • Architecture defines the package-wide data flow, result-capability protocol, provenance model, and the distinction between transformations, approximations, and numerical backends.
  • Core / Foundation defines state spaces, operator algebras, inspectable physical model-space admissibility, parameter spaces, reciprocal-space primitives, and ManyBodyModel.
  • Algebra implements noncommutative commutators, rewrite rules, normal ordering, and canonicalization.
  • Crystallography discovers space-group symmetry and generates invariant Hamiltonian bases.
  • Transformations represents exact maps, constrained embeddings, gauge-redundant maps, approximations, and transformation graphs.
  • Models defines geometry, materials, interactions, force constants, and Hamiltonian constructors.
  • Solvers covers computational bases, matrix realization, ED/Lanczos/time evolution, optimized packed backends, mode solvers, classical sampling, and cluster-perturbation Green functions.
  • Observables defines correlations, spectral functions, magnetic and nuclear neutron response, multiphonon scattering, and resolution convolution.
  • Thermodynamics provides exact Gibbs ensembles, stochastic thermal methods, symmetry-sector decomposition, and linked-cluster reconstruction.
  • Greens provides finite-temperature Matsubara propagators, Nambu indexing, Lehmann evaluation, Dyson relations, asymptotic moments, and validation diagnostics.
  • Embedding provides finite ED baths, impurity solvers, lattice/Weiss self-consistency, adaptive mixing, and the validated single-site ED-DMFT driver.
  • Workflows show how the layers compose without collapsing their mathematical distinctions.
  • Validation records the validation hierarchy, literature benchmarks, empirical checks, and the limits of the documented validation claims.

Documentation and validation scope

The manual describes the checked-out package source and the stated domains of its validation examples. Numerical benchmark results and regression counts refer to the particular recorded calculations, not to untested parameter regimes or every future revision. Current release and installation tags are maintained in the repository root README.md.

High-level forward calculation

A complete typed forward calculation can be planned before execution so that the selected computational route is inspectable:

plan = plan_forward(model, observable_request; probe=MagneticNeutronProbe(), resolution=GaussianResolution(0.08))
report = planning_report(plan)
result = forward(plan)

The conservative default execution policy considers only certified context-free exact routes and does not silently authorize a physical approximation. Explicit ForwardProblem construction remains available when the caller wants to choose the solver, transformation, or method context directly.

ForwardResult stores the source model, transformed working model, transformation result, solver output, intrinsic observable, probe-contracted scattering response, and final resolution-convolved result separately. This is the canonical package-level expression of the architecture.

The executable reference for this stable interface is demos/high-level-forward-api.jl. It demonstrates the public model/request/planner/forward sequence and prints the selected exact route together with the retained forward stages.

Note

Phundamental.Foundation is an alias of Phundamental.PhundamentalCore. The package does not define Phundamental.Core because Core is a built-in Julia module.

Note

The validated ED-DMFT implementation is normal-state, single-site, and single-orbital. The Green-function layer supports Nambu indexing, but superconducting/Nambu ED-DMFT remains outside the validated embedding scope.
